综合后，建议把项目定为：

# VPSHub：个人 VPS 统一运维管理平台

你的两份方案整体方向正确，但需要做几处调整：

1. **第一版不需要 Redis**：你只有约 50 台 VPS，SQLite WAL + 持久化任务队列足够，部署更简单。
2. **默认不开放 WebSSH**：WebSSH 权限太高，第一版应关闭，后续作为管理员手动开启的高风险功能。
3. **不要默认保存 root 密码**：优先使用独立管理用户 + 精确 sudo 权限，密码接入后自动转换为独立 Ed25519 密钥。
4. **不要长期维护 SSH 连接池**：批量任务使用短连接更安全；WebSSH 单独建立临时连接。
5. **必须增加灾难恢复机制**：主密码丢失无法解密凭据，因此必须支持加密备份、恢复密钥和主密钥轮换。
6. **脚本必须签名和审核**：不能只依靠危险命令检测。
7. **系统升级不能默认自动重启**：必须预检、灰度、失败暂停、重连验证。
8. **服务升级模块必须和普通脚本分开**：Xray、sing-box、Hysteria2、Komari 等应使用有备份和回滚能力的专用升级模块。

```markdown
# VPSHub 项目开发总指令

## 一、项目定位

开发一个自托管、单管理员优先、安全优先的 Linux VPS 统一管理平台，项目名称为 VPSHub。

平台用于集中管理约 50 台分布在不同服务商的 Linux VPS。每台 VPS 可能运行不同的探针、Docker、代理、网站、数据库、反向代理和其他脚本。

核心能力：

1. 通过 SSH 接入 VPS，无需默认安装常驻 Agent。
2. 自动扫描服务器系统、资源、Docker、systemd、监听端口和运行服务。
3. 统一查看每台 VPS 安装了什么、正在运行什么、哪些服务异常。
4. 批量执行经过审核的脚本。
5. 统一进行系统升级、Docker 更新、代理升级和探针升级。
6. 支持备份、健康检查、失败回滚和审计。
7. 支持后续增加轻量 Agent，但 Agent 不属于第一阶段核心依赖。

第一阶段只面向个人或小团队使用，不实现多租户、计费和云厂商 API。

VPSHub 面板作为 SSH 客户端，通过 SSH/SFTP 连接目标服务器。

- Go 后端

第一阶段不依赖 Redis、PostgreSQL、Kubernetes 或常驻 Agent。

未来可增加：

- PostgreSQL
- 多 Worker

## 四、安全模型

### 1. 主密钥和凭据加密

必须实现 Master Key 状态机：

- Locked
- Unlocked
- Expired

SSH 密码、SSH 私钥、私钥密码、sudo 密码、API Token 必须加密保存。

要求：

- 使用 Argon2id 从 Master Password 派生 KEK。
- 使用 AES-256-GCM 或 XChaCha20-Poly1305 加密数据。
- 每条凭据使用独立随机 nonce。
- 主密钥不能写入数据库。
- 面板重启后默认处于 Locked 状态。
- 未解锁时禁止任何 SSH 连接和任务执行。
- 支持自动锁定时间。
- 支持管理员手动锁定。
- 支持主密钥轮换。
- 支持加密备份和恢复。
- 支持生成离线恢复密钥。

注意：Go 的内存数据无法保证绝对清除，因此应尽量缩短明文凭据生命周期，禁止写入日志、临时文件和任务结果。

### 2. 登录安全

必须实现：

- 管理员密码使用 Argon2id 哈希。
- 强制 TOTP。
- 可选 WebAuthn/Passkey。
- HttpOnly、Secure、SameSite=Strict Cookie。
- 短期 Session。
- 登录失败限流。
- IP 和账号双重锁定。
- 可配置 IP 白名单。
- 强制退出所有会话。
- 首次登录必须修改初始密码。

优先使用安全 Cookie Session，不使用长期 JWT。

### 3. SSH 安全

必须实现：

- 密码认证。
- Ed25519 私钥认证。
- 跳板机。
- ProxyJump。
- SOCKS5 代理。
- IPv4、IPv6 和纯 IPv6。
- SSH Host Key 指纹校验。
- 禁止使用 InsecureIgnoreHostKey。
- 首次连接进入待确认状态。
- 指纹变化时阻止连接并告警。
- 每台 VPS 独立密钥。
- SSH 连接超时。
- 命令执行超时。
- 输出大小限制。
- 单机并发连接限制。

首次通过密码连接成功后，支持一键：

1. 生成独立 Ed25519 密钥。
2. 写入目标机 authorized_keys。
3. 使用新密钥验证。
4. 删除数据库中的密码。
5. 可选关闭目标机密码登录。
6. 关闭密码登录前必须二次确认并自动备份 sshd_config。

### 4. 最小权限

默认建议：

- 使用普通管理用户。
- 仅授予必要 sudo 权限。
- root 登录默认标记为高风险。
- 生产服务器和测试服务器必须区分。
- 高风险服务器需要额外标签和操作确认。

### 5. 危险操作

以下操作必须二次确认：

- 系统升级
- 重启服务器
- 修改 SSH
- 修改防火墙
- 删除 Docker 容器或卷
- 删除配置
- 关闭密码登录
- 批量执行脚本
- 批量重启服务
- 执行高风险脚本

批量任务必须：

- 显示目标服务器列表。
- 显示风险等级。
- 支持 Dry Run。
- 支持金丝雀服务器。
- 支持滚动批次。
- 支持失败率阈值。
- 达到失败阈值后自动暂停。

## 九、必须通过的验收测试

5. 单台 VPS 失败不影响其他 VPS。
6. 批量任务可以取消、重试和只重跑失败节点。
7. 生产环境默认不自动重启。
8. 代理升级失败可以恢复旧版本。
9. Docker Compose 更新前自动备份。
10. 所有高风险操作都有审计记录。
11. 普通脚本未经审核不能执行。
12. WebSSH 默认关闭。
13. Worker 重启后任务状态不会丢失。
14. 加密备份可以恢复。
15. 通过 go vet、gosec、依赖漏洞扫描和 SSH 集成测试。
```

## 还应额外补充的几个关键设计

### 1. 增加“只读模式”

VPS 可以设置为：

- 只读监控
- 可执行普通任务
- 可执行高风险任务
- 禁止所有变更

这样某些重要网站服务器可以只扫描状态，避免误操作。

### 2. 增加“维护窗口”

例如设置：

- 每周日凌晨 3 点允许系统升级。
- 白天只允许查看和重启服务。
- 非维护窗口执行高风险任务必须再次确认。

### 3. 增加“服务依赖关系”

例如：

- Nginx 依赖 Docker 容器。
- 代理服务依赖证书。
- 网站依赖数据库。
- 探针依赖网络服务。

升级或重启前，面板应提示可能影响的服务。

### 4. 增加“变更前后对比”

每次升级前后自动记录：

- 软件版本
- 监听端口
- systemd 状态
- Docker 容器状态
- 配置文件 SHA256
- CPU、内存、磁盘
- 健康检查结果

这样出现问题时可以快速判断到底改动了什么。

### 5. 增加“服务模板而不是盲目扫描”

扫描只能判断服务器当前状态，不能准确知道某个服务应该如何升级。因此：

- 扫描模块负责发现。
- 服务模板负责管理。
- 升级模块负责备份、升级和回滚。
- 脚本中心负责通用操作。

这四者需要分开设计。

最终建议是：**VPSHub 第一版先做到“安全接入、资产盘点、服务发现、批量任务、审计”，第二版再做各种代理和探针升级。** 这样架构稳定，也能避免一开始就因为大量危险脚本和升级逻辑导致系统失控。
